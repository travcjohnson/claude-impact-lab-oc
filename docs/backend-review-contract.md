# Backend review contract (BE-04, issue #5)

Status: **local prototype contract for the frontend owner; not agreed with BE-03.** All examples below were
generated by running the real code against a **synthetic fake adapter** (fixture field names, invented
text, `synthetic: true`). No model was called and no real document was read. IDs and timestamps are
placeholders. Reviewer names are free-text labels: there is **no authentication**, `reviewerId` is always
`null`, and history lives in server memory only (lost on restart).

## Endpoints added or changed

| Endpoint | Behaviour |
|---|---|
| GET `/api/referrals/{id}` | Unchanged record plus `allowedActions` (what may be done now, and why not) |
| PATCH `/api/referrals/{id}/review` | Page note, as before; response now includes `allowedActions` |
| PATCH `/api/referrals/{id}/fields/{fieldId}` | NEW. Body `{version, value, assessment: "verified"|"unresolved", reviewer, note?, page?}`. 200 returns the record plus `change` |
| POST `/api/referrals/{id}/outcome` | Now also requires every field reviewed; exact repeat returns 200 with `idempotentReplay: true` |
| GET `/api/referrals/{id}/export` | NEW. Current human-confirmed snapshot; 409 if there is no current confirmation |
| GET `/api/referrals/{id}/draft` | Now lists "CONFIRMED BY REVIEWER" and "OPEN / UNRESOLVED" fields |

## Rules (policy calls the team should confirm)

- The original extraction (value, status, evidence) is never overwritten. A correction is stored in `field.review` with reviewer label, note, source page, and full `history`.
- Only a field whose original status was `extracted` can be marked `verified`. Missing, redacted, conflicting and unreadable fields stay unresolved and need clarification or clinical review. **This is a conservative choice made without a clinical policy; confirm it.**
- A redacted value cannot be reconstructed; only `"unknown"` is accepted.
- A changed value needs a note of at least 12 characters and a source page that exists.
- Any field review bumps `version` and clears the confirmed outcome (so draft and export become unavailable). Findings that depend on a field whose effective value changed are marked `stale: true`, `reviewed: false`.
- A stale `version` gets 409 and nothing is applied. Two reviewers racing: the first wins, the second must reload.
- Confirmation is a repeat only if the request matches the stored one exactly; a different request at the same version gets 409.
- `approve` and `deny` are always `allowed: false`; the reasons are in `allowedActions`. Reasons are static text, never document content.

## Limitations

- Not exercised in the browser: the merged `backend-client.js` fails closed on any `analysis.status` other than `not_connected`, so the field-review UI needs FE-03 first.
- Synthetic fixtures only; no real extraction or model ID has been verified.
- No authentication, no durable history, no concurrent-process safety (single local process).
